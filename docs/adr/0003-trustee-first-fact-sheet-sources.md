# ADR 0003 — 便覽內容抓受託人官網，配對用積金局登記冊

日期：2026-09-11
狀態：已接受（追認 2026-08-31 起的實作）

## 背景

基金便覽（fund fact sheet）是配置、十大持倉兩項披露的唯一來源。兩個地方攞得到：

- **積金局便覽庫**（`mpfa.org.hk` 的計劃副本）：24 個計劃齊，連結抄錄自
  〈註冊強積金計劃及成分基金〉登記冊，穩定、有權威計劃編號。但存放的副本
  落後平台數據四至八個月。
- **受託人官網**：已經出到更新一期（部分新三至七個月），但名單本來就唔齊
  （AMTD 根本冇更新版），連結不預告改版，多個站係 JS render 加 bot 保護，
  而且冇一份權威嘅全行計劃清單。

兩邊各自缺一半：一邊夠齊但舊，一邊夠新但唔齊。

## 決定

**配對用積金局登記冊，內容抓受託人官網。**

1. 計劃名單同配對基準一律用 `data/sources/<YYYY-MM-DD>/fund-fact-sheet-links.json`，
   `assertFactSheetCoverage` 要求齊 24 個計劃，缺一個就報錯。
2. 內容優先用 `trustee-fact-sheet-links.json`（人手由受託人官網抄錄）。
   **呢份唔齊唔算錯**——抄到幾多得幾多。
3. 抽取層逐個計劃先試受託人那份，抽唔到（官網改版、下載失敗、版面對唔上契約）
   就退回積金局副本，並把原因寫入覆蓋報告的 `trusteeFallbackReason`。
   退回本身唔係錯，但唔可以靜靜哋當成最新版。
4. 每筆披露帶住 `factSheetSource`（`trustee` / `mpfa-registry`）及 `factSheetUrl`，
   詳情頁按來源講明措辭並連去實際用咗嗰份便覽。
5. 連結逐筆明寫 `file`（本機檔名），唔靠 URL 尾段推算。

## 否決方案

- **全部用積金局副本。** 配置同持倉會落後平台回報四至八個月，同一版網頁上
  兩組數字期別相差太遠，而且已知副本會漏收新成分基金（友邦漏 Retirement
  Income Fund、我的強積金漏三隻新基金）。
- **全部用受託人官網。** 冇權威計劃清單做配對基準，AMTD 一個計劃直接冇著落，
  亦冇辦法斷言覆蓋齊全。
- **自動爬受託人官網搵連結。** 多個站行 Cloudflare／Akamai／CloudFront，連結
  格式各自不同且會不預告改版（BCT Pro Choice 的短連結根本唔係 `PC-` 開頭，
  東亞 2026 年起由一份共用檔拆成逐計劃一份）。靠推算等於隨時攞錯計劃的便覽
  貼落去，所以逐筆人手抄錄。

## 後果

- 24 個計劃之中 23 個已換上受託人版，資料新三至七個月；AMTD 維持積金局副本
  `MT00539.pdf`（2025-12-31），因為受託人官網本身冇更新版。
- 換版一律要先跑覆蓋報告比對，確認配對數、配置數、持倉數冇退步先可以換。
  呢個流程實際攔截過兩次退步（新地少一隻持倉、Series 800 兩個 band 重疊）。
- 一個計劃可以有多份便覽（富達 23 份、MASS 14 份），所以來源檔加咗
  `funds` 形態，並要求逐份對名。
- 每筆披露各自保留自己的 `factSheetAsOf`，唔可以沿用平台的 `dataAsOf`。

## 重審條件

- eMPF 平台開始統一刊發便覽——嗰陣單一來源可能同時夠齊又夠新。
- 積金局副本的期別差距收窄到一季以內。
