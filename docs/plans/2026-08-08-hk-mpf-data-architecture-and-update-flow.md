# 香港強積金比較網站：資料架構及更新流程規劃

研究日期：2026-08-08
狀態：規劃中，未開始實作

## 目的

把已確認的產品規格及資料字典轉成可供日後實作的技術邊界，確保資料取得、標準化、排名及展示可以分開驗證，並保留每項結果的來源及版本。

## 主要架構

```text
官方平台／官方文件／可靠第三方
              ↓
      原始資料及來源版本層
              ↓
       擷取、解析、驗證流程
              ↓
       標準化基金資料層
              ↓
        比較及排名引擎
              ↓
       網頁搜尋、比較及詳情頁
```

### 原始資料層

每次取得資料都保存來源網址、來源類型、文件或頁面日期、擷取時間、原始內容版本及解析狀態。原始資料不可被標準化流程覆寫，方便重跑、追溯及調查差異。

### 標準化資料層

把計劃、成分基金及 `fund_class` 關聯起來，統一基金類別、資產配置、回報期間、風險指標、費用及資料日期。每個欄位保留來源引用、驗證狀態及有效版本，而不是只保存最後一個數值。

### 比較及排名引擎

排名引擎只讀取已驗證的標準化資料，不直接讀取網頁或文件。它應分開產生基金類別／配置、回報及風險結果；資料不足、待核實或非完全可比的資料不得靜默轉成可排名數值。

### 展示層

展示層提供基金篩選排名、計劃比較及詳細基金頁。每個數值可追溯至標準化欄位及原始來源；簡化頁先顯示結論，詳細頁再展開定義、日期、費用拆分及限制。

## 每日更新流程

1. 建立當日更新批次及來源清單。
2. 並行取得 MPF Fund Platform、MPFA 官方登記／披露資料及受託人最新文件；可靠第三方只補充官方未覆蓋欄位。
3. 保存原始版本，記錄取得成功、失敗或內容沒有變化。
4. 解析及標準化資料，將基金名稱、基金類別、費用及期間轉成統一格式。
5. 進行結構檢查、數值檢查、日期檢查及來源交叉核對。
6. 判定基金是否仍屬現行可供選擇；平台、受託人名單及官方文件未能一致確認時，標示「待核實」並排除排名。
7. 只有通過驗證的資料才建立新的可展示版本。
8. 重新計算受影響基金及計劃的比較結果。
9. 執行展示及來源可追溯性檢查。
10. 更新成功則發布新版本；失敗則保留上一個已驗證版本，並記錄失敗原因及受影響範圍。

部分來源失敗不必阻止未受影響資料發布。新快照可沿用受影響欄位的上一個已驗證值，但必須保留原截至日期及過期狀態；過期沿用值不得參與相關指標排名。

## 驗證規則

### 完整性

- 計劃、受託人及 `fund_class` 關係不可缺失。
- 回報、風險及費用數值必須有資料截至日期、來源及驗證狀態。
- 現行基金數量出現異常大幅變化時，批次進入待核實狀態。

### 數值及定義

- 回報期間、年化／累積定義及是否已扣除費用必須明確。
- 風險指標按三年每月回報年化標準差處理；不足三年顯示資料不足。
- FER 與當前管理費、其他費用及 OCI 分開保存及展示。
- 不以零、估算值或跨類別替代值填補缺失資料。

### 可比性

- 持倉及資產配置優先比較同一截至日期及分類。
- 日期或分類有小幅差異時標示「非完全可比」。
- 無法合理對齊時只展示原始資料，不建立合併排名。

### 過期判定

- 每個來源及資料類型分別記錄預定發布周期及寬限期，不使用全站統一日數。
- 超過預定周期及寬限期後轉為 `stale`；仍可展示最近已驗證數值及截至日期，但不得參與相關指標排名。
- 月度回報及基金規模的期限為相關月結後 45 日。
- 基金概覽內的持倉、資產配置、風險及 FER，以每個計劃的財政年結日及適用法定發布期限計算，寬限期為期限後 30 日。
- 現行基金狀態每日核實；連續 7 日未能成功核實時暫停相關基金排名並轉交人工核對。
- 來源發布安排改變時，可修改日後批次的期限設定，但不可追溯改寫既有批次狀態。

### 回報與風險序列

- 自訂期間以扣除基金層面費用後的單位價格作點對點計算，只展示及排序累積回報，不作年化。
- 自訂期間缺少相同起訖月價格時不得插值；該基金不參與該期間排名。
- 三年風險指標所需月度序列缺少任何月份時不得插值；顯示資料不足並排除風險排序。
- 百分比統一顯示至小數點後兩位，並以相同顯示精度判定並列名次。

### 人工核對門檻

以下任何情況均阻止候選批次自動發布，並要求人工核對：基金新增、移除或身份改變；同一截至日期數值被修訂；單月回報絕對值超過 30%；配置合計不在 99% 至 101% 之間；任何費率改變；或主要來源連續兩次失敗。

異常門檻以版本化設定保存。人工批准只能批准或拒絕完整候選批次，不得跳過驗證或直接修改正式資料。

## 資料狀態

| 狀態 | 展示 | 可否排名 |
|---|---|---|
| verified | 可以 | 可以，視乎其他條件 |
| stale | 可以，但醒目顯示資料日期 | 不可以參與相關指標排名 |
| insufficient | 可以，顯示資料不足 | 不可以 |
| pending_verification | 可以或暫時隱藏 | 不可以 |
| source_conflict | 顯示衝突及來源 | 不可以 |
| failed_with_last_verified | 顯示上一個已驗證版本及舊日期 | 可以沿用上一版本 |

## 版本及回退

每個成功批次應產生不可變版本，並記錄來源版本、標準化版本及展示版本之間的關係。新批次未通過驗證時不可覆寫目前展示版本；系統應保留上一個已驗證版本，並在管理紀錄中指出哪些來源失敗或數值被拒絕。

所有曾支援公開發布快照的原始文件及來源版本長期保留；D1 亦長期保留發布歷史及稽核關係。只有未支援任何公開快照的候選或失敗資料可按保留政策清理。

未發布候選批次保留 90 日，失敗擷取內容保留 30 日；已進入人工調查的資料暫停自動刪除，直至調查結案。自動清理前必須確認資料未被任何公開快照引用。

異常批次在第一版透過 GitHub Actions 核對報告及 artifact 供人工審閱，只有人工批准 workflow 後才可發布；第一版不另建管理網站。

人工批准由 GitHub production environment 的 required reviewer 保護，並保留批准人、時間、候選批次及核對報告的稽核關係。

## 災難復原

- D1 Time Travel 用於短期時間點復原。
- D1 每週完整匯出至獨立 R2 備份位置並保留一年。
- 每季在非正式環境執行實際還原測試。
- 被公開快照引用的 R2 原始文件及 manifest 不受自動清理規則影響。

## 尚待技術方案階段決定

- 原始資料及標準化資料採用的儲存格式。
- 每個來源的擷取工具及文件解析方式。
- 具體網站框架及 Cloudflare 專案設定。
- 實際 Cloudflare 帳戶及方案的容量與執行限制核對。
- 排名引擎的具體排序、同分及自訂期間演算法。
- 網站部署方式及每日更新的排程工具。

以上項目會在確認技術方案後決定；目前不代表已選定資料庫、框架或部署平台。

## 驗收方向

- 可由任一展示數值追溯至標準化欄位及原始來源。
- 任一來源失效時，不會產生未標示的估算值或空白排名。
- 未被三方資料一致確認為現行的基金不會進入排名。
- FER、當前管理費、其他費用及 OCI 在詳細頁保持分開。
- 同日同分類資料優先；不能完全比較時，介面明確顯示限制。
- 更新批次失敗時，網站仍能顯示上一個已驗證版本及其資料日期。
