# 香港強積金比較網站：第一版實作規格

日期：2026-08-08  
狀態：已確認；未開始實作  
文件角色：第一版實作及拆票的 canonical spec

本文件整合並取代較早文件中互相重疊的第一版範圍及實作描述。領域用語以根目錄 `CONTEXT.md` 為準；部署原因以 ADR 0001 為準；來源定義及研究引用仍以資料字典文件為準。

## Problem Statement

香港強積金計劃、成分基金及基金類別資料分散於積金局平台、公共登記冊、受託人網站及不同格式的官方文件。一般打工仔難以在相同定義、相同期間及相同基金種類下比較基金；較有投資經驗的用戶亦難以同時核對回報、風險、費用、配置及持倉。資料更新時間不一致、同名基金具有不同基金類別，以及官方平台與最新文件之間可能有時間差，令普通排名容易產生誤導。

第一版需要提供一個免費、無廣告、繁體中文優先的比較工具，涵蓋所有現行可供選擇的香港強積金計劃、成分基金、基金類別及預設投資策略。網站只整理、解釋及比較公開資料，不提供個人化投資建議、基金轉換指示或單一推薦分數。

## Solution

建立一條可追溯的資料及發布路徑：

`官方平台／文件 → 原始資料封存 → 標準化及驗證 → 發布快照 → 比較／排名引擎 → 網頁展示`

公開網站提供三個核心流程：

1. 按基金種類、配置、期間及風險條件篩選基金，然後在同一比較組別內查看回報或波幅排序。
2. 比較強積金計劃、受託人、基金選擇數量及基金種類分布。
3. 查看基金類別詳情，包括投資目標、配置、回報、風險、費用、持倉、來源、日期及資料限制。

基金種類及資產配置用於建立可比較組別，不會成為跨類別加權分數。回報與風險分開排序，不合成總分。公開查詢只讀取不可變的發布快照；候選批次未經驗證不得直接影響網站。

## User Stories

1. 作為一般打工仔，我想先按基金種類及配置縮窄範圍，以便只比較投資目標相近的基金。
2. 作為一般打工仔，我想按投資年期及風險取向調整篩選條件，以便理解哪些比較組別值得進一步研究，而不是收到個人化推薦。
3. 作為一般打工仔，我想在同一比較組別查看 1、3、5 及 10 年回報，以便分辨不同期間的表現。
4. 作為一般打工仔，我想分開查看回報排序及較低波幅排序，以免把低波幅或高回報誤解為整體較佳。
5. 作為一般打工仔，我想知道每項排名所使用的指標、方向、期間及比較組別，以便理解名次的含義。
6. 作為一般打工仔，我想看到基金資料的來源及截至日期，以便判斷資料是否最新。
7. 作為一般打工仔，我想看到「過期」、「待核實」、「資料不足」及「非完全可比」等狀態，以便理解資料限制。
8. 作為一般打工仔，我想搜尋基金、計劃或受託人名稱，以便快速找到已有強積金選擇。
9. 作為一般打工仔，我想在手機及電腦完成相同核心流程，以便在不同情境查閱資料。
10. 作為投資經驗較豐富的用戶，我想選擇不少於 12 個完整月份的自訂期間，以便比較相同起訖月份的累積回報。
11. 作為投資經驗較豐富的用戶，我想自訂期間只使用可驗證、扣除基金層面費用後的單位價格，以免來源定義混雜。
12. 作為投資經驗較豐富的用戶，我想比較資產、地區、行業及主要持倉，以便理解基金實際曝險。
13. 作為投資經驗較豐富的用戶，我想知道持倉或配置是否非同日或非同分類，以免把不完全一致的資料當成精確比較。
14. 作為投資經驗較豐富的用戶，我想分開查看 FER、當前管理費、其他費用及 OCI，以便分辨歷史費用與現行費率。
15. 作為僱主或 HR，我想比較計劃旗下基金數量、種類及風險分布，以便初步評估員工可用的投資選擇。
16. 作為僱主或 HR，我想從計劃層級進入旗下基金詳情，以便追查計劃比較結果。
17. 作為所有用戶，我想相同顯示數值得到相同名次，以免名次被未顯示的小數或隱藏指標打破。
18. 作為所有用戶，我想過期數值仍可連同原日期查看，但不參與相關排名，以便保留資訊而不污染排序。
19. 作為所有用戶，我想清楚看到資料比較不等於投資建議，以及過往表現不代表未來結果。
20. 作為資料核對者，我想每個公開數值都能追溯至標準化欄位及原始來源，以便調查錯誤或來源差異。
21. 作為資料核對者，我想異常批次提供完整核對報告及 artifact，以便批准或拒絕整個候選批次。
22. 作為資料核對者，我想批准流程不能跳過驗證或直接改寫正式資料，以便維持發布完整性。
23. 作為營運者，我想部分來源失敗時只沿用受影響欄位的上一個已驗證值，以便未受影響資料仍可更新。
24. 作為營運者，我想沿用值保留原截至日期及過期狀態，以免被誤認為新資料。
25. 作為營運者，我想更新失敗時網站繼續讀取上一個可用發布快照，以免公開頁面中斷。
26. 作為營運者，我想每週保存 D1 完整匯出並每季驗證還原，以便在超出短期時間點復原範圍後仍能復原。
27. 作為未來維護者，我想所有狀態、門檻及來源關係都有版本紀錄，以便知道某次發布使用了哪些規則。

## Implementation Decisions

### 產品及範圍

- 用戶優先次序為一般打工仔、投資者、僱主／HR。
- 第一版繁體中文優先，手機及電腦同等重要。
- 第一版免費、無廣告，不設登入或付費功能。
- 涵蓋所有現行可供選擇的計劃、成分基金、基金類別及預設投資策略；歷史或停止接受新供款的基金不納入第一版。
- 第一版頁面為基金篩選及排名、計劃比較、基金類別詳情。

### 部署及模組邊界

- GitHub Private repository 是唯一程式碼來源。
- Cloudflare Pages 負責前端，Workers 負責 API、Cron 及發布控制，D1 保存標準化資料、排名及發布狀態，R2 保存原始文件、候選 artifact、manifest 及備份。
- GitHub Actions 負責擷取、PDF 解析、標準化、交叉核對及產生候選批次。
- Source adapters、raw archive、normalizer、validator、publication snapshot 及 comparison engine 是分開的模組。
- 網站及 API 不在請求期間擷取官方來源；只讀取目前發布快照。
- 具體前端框架、D1 schema 及 Cloudflare 配置在建立專案時選定，但不得改變上述 seam。

### 資料來源及最小單位

- MPF Fund Platform 是主要日常標準化來源；MPFA 公共登記冊、計劃文件庫及受託人最新文件作交叉核對。
- 官方文件是來源衝突時的最終核對依據；可靠第三方只補充官方未覆蓋欄位，不得覆寫官方定義或數值。
- `fund_class` 是最小比較單位，並保留其所屬成分基金、計劃及受託人關係。
- 每個時間性數值必須保存 `data_as_of`、來源、擷取時間、原始值、標準化值及驗證狀態。
- 現行狀態須由平台、受託人名單及官方文件一致確認；未能確認者為「待核實」並排除排名。

### 資料狀態及可比性

- 支援 `verified`、`stale`、`insufficient`、`pending_verification`、`source_conflict` 及 `failed_with_last_verified` 狀態。
- 過期資料可展示，但不參與相關指標排名。
- 缺失資料不可用零、平均值、前值或插值補足。
- 持倉及配置優先使用同日同分類資料；存在可接受日期或分類差異時標示「非完全可比」，不能合理對齊時只展示而不合併排名。
- 部分來源失敗時，新快照可沿用受影響欄位的上一個已驗證值；沿用值保留原日期及狀態，未受影響資料可照常更新。

### 過期政策

- 月度回報及基金規模在相關月結後 45 日未取得新一輪已驗證資料，轉為 `stale`。
- 持倉、資產配置、風險及 FER 依每個計劃的財政年結日及適用基金概覽發布期限計算；法定期限後 30 日仍未取得已驗證資料，轉為 `stale`。
- 現行基金狀態每日核實；連續 7 日未成功核實時暫停相關基金排名並進入人工核對。
- 發布安排日後改變時只修改後續批次期限，不追溯改寫歷史狀態。

### 排名規則

- 基金種類及配置先建立比較組別；只在同一組內排序。
- 預設提供 1、3、5 及 10 年回報視圖；使用來源已驗證的相應累積及／或年化欄位，並清楚顯示定義。
- 自訂期間只接受完整月份，最短 12 個月；只比較覆蓋相同起訖月份的基金。
- 自訂期間使用扣除基金層面費用後的單位價格作點對點累積回報，只展示及按累積回報排序，不年化。
- 自訂回報缺少相同起訖月價格時排除，不插值。
- 三年風險指標需要完整月度序列；缺少任何月份即顯示資料不足並排除風險排序。
- 回報與風險分開排序，不設綜合或推薦總分。
- 風險預設由低波幅至高波幅，名稱為「較低波幅排序」，並容許反向排序。
- 百分比顯示至小數點後兩位，並按相同顯示精度判定並列；採用競賽排名，例如第 1、第 1、第 3。
- `insufficient`、`pending_verification`、`source_conflict`、`stale` 及不可合理比較資料不參與相關排名。

### 費用展示

- FER、當前管理費、其他費用及 OCI 分開保存。
- 簡化列表只顯示主要費用及資料日期；基金詳情提供完整拆分及定義。
- FER 標示為上一財政期的歷史數據，不得當作當前管理費。

### 更新、異常及批准

- 更新階段為 `collect → parse → normalize → validate → calculate → publish`，每階段可獨立重試。
- 正常批次自動發布；異常批次不得自動發布。
- 以下任何一項觸發人工核對：基金新增、移除或身份改變；同一截至日期數值被修訂；單月回報絕對值超過 30%；配置合計不在 99% 至 101%；任何費率改變；主要來源連續兩次失敗。
- 異常門檻配置化及版本化，只有根據實際誤報或漏報證據才調整。
- GitHub Actions 產生核對報告及 artifact；GitHub production environment 的 required reviewer 只能批准或拒絕完整候選批次。
- 批准流程不能跳過驗證，公開網站不能成為人工修改資料的入口。

### 保存及災難復原

- 支援公開快照的所有 R2 原始文件、來源版本及 manifest 長期保留，不受自動清理影響。
- 未發布候選批次保留 90 日；失敗擷取內容保留 30 日；調查中資料暫停清理直至結案。
- D1 長期保留發布快照、批次、來源及稽核關係。
- 使用 D1 Time Travel 作短期時間點復原。
- 每週完整匯出 D1 至獨立 R2 備份位置並保留一年。
- 每季在非正式環境執行實際還原測試並保存結果。

### API 及公開行為

- 公開 API 只需支援基金篩選／排名、計劃比較、基金類別詳情及搜尋所需讀取能力。
- 所有查詢在一次回應內使用同一發布快照識別碼。
- 搜尋、排序及自訂期間不改變資料版本。
- API 及頁面必須回傳或顯示來源、截至日期、資料狀態及比較限制。
- 內部錯誤、秘密、未處理原始內容及候選資料不得出現在公開回應。

## Testing Decisions

### 主要測試 seam

最高測試 seam 是「已驗證標準化資料及發布快照 → 比較／排名引擎 → 公開 API／頁面結果」。測試以外部可見結果為主，不把 adapter 或資料庫內部結構當作產品行為。

### 必要測試組別

- 來源 adapter contract tests：固定官方樣本可解析，格式改變時明確失敗，不產生半解析數值。
- 標準化 tests：名稱、關係、日期、百分比、費用及類別映射保留原始值與來源。
- 現行狀態 tests：三方一致才進入排名；衝突時為待核實。
- 比較組別 tests：不同基金種類不會進入同一排名，配置只決定組別而不產生權重。
- 預設期間 tests：1、3、5、10 年資料不足、過期及來源衝突時正確排除。
- 自訂期間 tests：少於 12 個月、不完整月份、起訖月缺失及不同起訖月份均不可排名；有效資料只計累積回報。
- 風險 tests：三年完整月度序列才可計算；任何缺月不插值。
- 排名 tests：兩位小數、並列第 1／第 1／第 3、正反排序及較低波幅命名。
- 狀態 tests：過期資料可見但不排名；沿用值保留舊日期；不可比資料有明確標示。
- 費用 tests：FER、當前管理費、其他費用及 OCI 不會互相覆寫。
- 發布 tests：候選資料不公開；正常批次自動發布；異常批次等待批准；拒絕後維持舊快照。
- 部分失敗 tests：未受影響欄位更新，受影響欄位沿用上一已驗證值，整個回應仍使用單一快照。
- 異常門檻 tests：六類門檻逐一觸發人工核對，配置版本可追溯。
- 追溯 tests：任一公開數值可連回標準化欄位、來源文件及擷取版本。
- 回退 tests：失敗更新不覆寫現有快照；D1 匯出可在非正式環境還原並通過快照完整性檢查。
- UI tests：手機及電腦均可完成搜尋、篩選、排名、計劃比較及詳情流程；狀態、日期、來源及免責聲明可見。

### 驗收閘門

- 所有公開基金均符合現行三方核對規則。
- 每個公開數值都有來源及截至日期。
- 任一 ranking fixture 可由規格規則重算得到相同名次。
- 任一異常候選批次不能繞過 required reviewer 發布。
- 任一來源失敗不會導致未標示估算值、錯誤清空或跨快照混合。
- 每季還原演練可重建一個可查詢且來源關係完整的非正式環境。

## Out of Scope

- 個人化投資建議、風險適合性判斷、買賣或基金轉換指示。
- 單一綜合分數、推薦榜、贊助排名或廣告。
- 已停止接受新供款的歷史基金。
- 登入、觀察清單、個人投資組合及通知。
- HR 報告生成、匯出及完整行政服務評分。
- 英文版。
- 交易、即時市價或預測未來回報。
- 獨立管理網站或在公開網站直接修正資料。
- 在第一版公開第三方計算值取代官方定義。

## Further Notes

- 「每日更新」指每日執行擷取及驗證流程，不代表每個來源每日發布新資料。
- 年齡、投資年期及風險取向只用作教育式篩選及比較組別導覽，不輸出「適合你」或「應選擇」的基金。
- 原始網址及文件視為不可信輸入；解析需要檔案大小、格式、執行時間及內容安全限制。
- 建立專案前仍需核對實際 Cloudflare 帳戶方案限制、選定網站框架、配置 GitHub issue tracker／labels，以及建立最小權限 Cloudflare token。這些是實作準備事項，不改變本規格的產品行為。
- 本規格獲確認後，下一步是用 `to-tickets` 草擬 tracer-bullet tickets；正式發布至 GitHub 前需先建立或指定 repository 及 tracker 設定。
